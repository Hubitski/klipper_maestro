# Технический аудит и ревизия реализации Klipper для Maestro Grand 2 IDEX

**Дата:** 25 сентября 2026 г.  
**Статус:** Выявлены критические дефекты (Show-stoppers). Прошивка и стек **не готовы** к установке на принтер.  
**Цель документа:** Детальная фиксация всех обнаруженных ошибок, архитектурных просчетов и составление пошагового плана исправлений.

---

## 1. Введение и резюме аудита

В ходе выполнения плана `MAESTRO_GRAND2_KLIPPER_ARCHITECTURE.md` предыдущий агент допустил забегание вперед: вместо того чтобы ограничиться стабильным протоколом полудуплексной адресации, аппаратным роутером и хостовым мультиплексором, были преждевременно созданы высокоуровневые файлы конфигурации принтера (`printer.cfg`), содержащие грубые ошибки настройки механики.

При этом в **самом ядре протокола и маршрутизации** были допущены **4 критических системных бага**, из-за которых система в текущем виде физически не способна работать на реальном железе:
1. **Коллизии на полудуплексной шине MCP2561** из-за некорректного условия включения передатчика в слейв-режиме.
2. **Разрушение кадров (байт-интерливинг)** в аппаратном роутере материнской платы из-за отсутствия межкадровой синхронизации USART0/USART1.
3. **Спонтанная генерация NAK** периферийными платами при шумах или приеме чужих поврежденных кадров.
4. **Неверный битрейт (230 400 вместо 250 000 бод)** на хосте из-за некорректного использования модуля `termios` в Python.

Ниже приводится подробный разбор каждой проблемы с указанием файлов и строк кода, а также план их решения.

## 2. Реестр выявленных дефектов

### Дефект №1 (КРИТИЧЕСКИЙ): Аппаратные коллизии на шине MCP2561 при приеме пакетов для других плат
* **Файл:** `src/generic/serial_irq.c`, строки 81–92.
* **Суть проблемы:**
  В функции `console_task()`:
  ```c
  int_fast8_t ret = command_find_block(receive_buf, rpos, &pop_count);
  if (ret > 0)
      command_dispatch(receive_buf, pop_count);
  if (ret) {
      console_pop_input(pop_count);
      if (ret > 0)
          command_send_ack();
  #if CONFIG_SERIAL_POLLED_SLAVE
      if (readb(&transmit_pos) < readb(&transmit_max))
          serial_enable_tx_irq();
  #endif
  }
  ```
  В `command_find_block()`, когда плата (например, Head 0 с Node ID `0x20`) видит пакет для другой платы (например, Head 1 с Node ID `0x30`), она выполняет `silent drop` и возвращает значение **`-1`**.
  В условии `if (ret)` значение `-1` трактуется как **истина (true)**!
  Если у платы Head 0 в этот момент в `transmit_buf` был накоплен хотя бы один байт отчета (например, периодический опрос АЦП температуры сопла), Head 0 **немедленно активирует `serial_enable_tx_irq()` и начинает выгружать данные в общую шину MCP2561 ровно в тот момент, когда Head 1 отвечает хосту!**
* **Последствие:** Два микроконтроллера вещают в полудуплексную дифференциальную пару одновременно. 100% коллизия, потеря пакетов, аварийный останов Klipper (`Lost communication with MCU`).
* **Необходимое исправление:** Вызов `serial_enable_tx_irq()` на ведомом узле должен находиться **строго внутри `if (ret > 0)`** — ведомый имеет право отвечать только тогда, когда валидный пакет пришел лично ему.

### Дефект №2 (КРИТИЧЕСКИЙ): Разрушение пакетов (Интерливинг) в аппаратном роутере ATmega1284p
* **Файлы:** `src/avr/serial.c` (строки 97–112) и `src/avr/maestro_router.c`.
* **Суть проблемы:**
  Вектор прерывания готовности передатчика `USARTx_UDRE_vect` на материнской плате реализован следующим образом:
  ```c
  ISR(USARTx_UDRE_vect)
  {
  #if CONFIG_MAESTRO_ROUTER
      uint8_t rdata;
      if (maestro_router_get_tx0(&rdata) == 0) {
          UDRx = rdata;
          return;
      }
  #endif
      uint8_t data;
      int ret = serial_get_tx_byte(&data);
      if (ret)
          UCSRxB &= ~(1<<UDRIEx);
      else
          UDRx = data;
  }
  ```
  Здесь происходит побайтовое подмешивание данных без учета границ кадров (Frame-level Interlocking).
  **Сценарий катастрофы:**
  1. Локальный Klipper материнки передает хосту длинный ответ (например, статус концевиков или шаговых двигателей — 12 байт). Передано 3 байта.
  2. В этот момент из шины периферии (USART1) от каретки Head 0 прилетает ответ на ранее отправленный запрос.
  3. На очередном прерывании `USART0_UDRE` функция `maestro_router_get_tx0()` возвращает `0` и **вклинивает байт от каретки прямо в середину пакета материнки!**
  4. Если между байтами от каретки на USART1 возникает микросекундная пауза (джиттер/стоп-бит), роутер переключается обратно на материнку и шлет байт материнки, а затем снова байт каретки.
* **Последствие:** Поток данных к хосту превращается в перемешанную кашу байтов двух разных MCU. Обе контрольные суммы CRC16 ломаются. Klipper закрывает соединение из-за фатальной ошибки CRC.
* **Необходимое исправление:** Ввести атомарную межкадровую блокировку: если материнка начала передавать пакет в USART0, байты из USART1 буферизируются до завершения кадра (до байта `0x7E`). Аналогично, если начата передача кадра от периферии в USART0, локальный Klipper материнки блокируется до передачи завершающего байта `0x7E`.

### Дефект №3 (КРИТИЧЕСКИЙ): Спонтанная отправка NAK на общей шине ведомыми платами
* **Файл:** `src/command.c`, строки 337–359.
* **Суть проблемы:**
  В `command_find_block()`, если на шине возникает шум, сбой синхронизации или искажение контрольной суммы, код переходит на метку `nak:`:
  ```c
  nak:
      command_sendf(&encode_acknak);
      return -1;
  ```
  В режиме `CONFIG_SERIAL_POLLED_SLAVE` ведомый узел **категорически не должен** спонтанно слать NAK на шину при неопознанных или поврежденных байтах.
  Если на линии проскочит помеха во время передачи пакета к Head 0, и Head 1, и Bed также увидят битый фрейм и одновременно попытаются выплюнуть в шину NAK.
* **Последствие:** Лавинообразные коллизии NAK-пакетов при малейшей помехе в проводке принтера.
* **Необходимое исправление:** В режиме `CONFIG_SERIAL_POLLED_SLAVE` переход на `nak:` должен быть заблокирован: ведомый узел должен выполнять тихий сброс (`silent drop`) до следующего байта `0x7E`.

### Дефект №4 (КРИТИЧЕСКИЙ): Ошибка скорости 250 000 бод в хостовом мультиплексоре (`host_multiplexer.py`)
* **Файл:** `scripts/maestro/host_multiplexer.py`, строки 245–253.
* **Суть проблемы:**
  В коде открытия физического порта:
  ```python
  baud_const = getattr(termios, f"B{self.baud_rate}", None)
  if baud_const is None:
      logging.warning("Standard baud constant B%d not found in termios, using 250000 fallback", self.baud_rate)
      baud_const = getattr(termios, "B230400", termios.B115200)
  ```
  В стандартном Python на Linux в модуле `termios` константа `B250000` **отсутствует** (POSIX стандартизирует скорости только до B115200/B230400).
  В итоге скрипт молча откатывается на **230 400 бод**!
  Микроконтроллеры же жестко зашиты на **250 000 бод**.
  Разница скоростей составляет **8.5%** (при максимальном допуске для UART не более 2.5%).
* **Последствие:** Связи с платами не будет вообще. Хост будет считывать только бесконечный битовый мусор и framing errors.
* **Необходимое исправление:** Использовать модуль `pyserial` (`serial.Serial(port, 250000)`), который штатно входит в зависимости Klipper и аппаратно корректно конфигурирует кастомную скорость 250 000 бод через интерфейс ядра Linux `TCSETS2` / `termios2`.

### Дефект №5 (ВЫСОКИЙ): Зависание мультиплексора на 100% CPU при рестарте Klipper
* **Файл:** `scripts/maestro/host_multiplexer.py`, строки 327–330.
* **Суть проблемы:**
  При старте Klippy или при перезапуске сервиса клиент закрывает дескриптор виртуального PTY.
  В цикле `poll.poll()` на мастере PTY возникает постоянное событие `POLLHUP`.
  Скрипт мультиплексора просто выводит лог:
  ```python
  if event & (select.POLLERR | select.POLLHUP):
      logging.warning("Channel %s closed by client, waiting...", chan.name)
  ```
  Но дескриптор **не удаляется** из `poll` и PTY **не пересоздается**!
  В результате `poll.poll()` начинает мгновенно возвращать управление без задержки, вводя поток в бесконечный цикл со **100% загрузкой процессора Orange Pi**, а при повторном подключении Klippy виртуальный порт оказывается сломан.
* **Необходимое исправление:** Реализовать корректное переоткрытие PTY-пары и перерегистрацию в `select.poll` при получении `POLLHUP`/`POLLERR`.

### Дефект №6 (СРЕДНИЙ): Пропущенные макросы для чипа ATmega16 в подсистемах SPI и ШИМ
* **Файлы:**
  - `src/avr/spi.c` (строки 17–33)
  - `src/avr/hard_pwm.c` (строки 24–44)
  - `src/avr/i2c.c` (строки 18–30)
* **Суть проблемы:**
  Чип `CONFIG_MACH_atmega16` был добавлен в `src/avr/Kconfig`, но не был включен в таблицы регистров для SPI и аппаратного ШИМ:
  1. В `src/avr/spi.c` отсутствуют определения пинов `MISO`, `MOSI`, `SCK`, `SS` для ATmega16. При сборке с включенным SPI компилятор выдает фатальную ошибку `undeclared identifier`.
  2. В `src/avr/hard_pwm.c` массив `pwm_regs[]` для ATmega16 компилируется пустым. Любая попытка назначить аппаратный ШИМ приводит к падению прошивки в `shutdown("Not a valid PWM pin")`.
* **Необходимое исправление:** Добавить ветку `#elif CONFIG_MACH_atmega16` в `spi.c`, `hard_pwm.c` и `i2c.c` в соответствии с распиновкой ATmega16 (совпадает с ATmega644p/1284p).

### Дефект №7 (СРЕДНИЙ): Отсутствие проверки переполнения кольцевого буфера роутера
* **Файл:** `src/avr/maestro_router.c`, строки 33–39.
* **Суть проблемы:**
  Функция `fifo_put()` инкрементирует `head` без проверки дистанции до `tail`:
  ```c
  static inline void fifo_put(struct router_fifo *f, uint8_t b) {
      uint8_t h = f->head;
      f->buf[h & ROUTER_BUF_MASK] = b;
      f->head = h + 1;
  }
  ```
  Если буфер (128 байт) заполняется, старые данные тихо перезаписываются, что приводит к разрыву и искажению проходящих пакетов.
* **Необходимое исправление:** Добавить проверку переполнения `(uint8_t)(f->head - f->tail) >= ROUTER_BUF_SIZE` с отбрасыванием повреждаемого пакета до маркера `0x7E`.

### Дефект №8 (ЗАБЕГАНИЕ ВПЕРЕД): Проблемы в преждевременно созданном `printer_maestro_grand2_idex.cfg`
* **Файл:** `scripts/maestro/printer_maestro_grand2_idex.cfg`.
* **Суть проблемы:**
  Конфиг принтера был написан до реальной отладки прошивки и содержит опасные параметры:
  1. `restart_method: arduino` на виртуальных PTY — неприменимо (PTY не имеют DTR, слейвы на MCP2561 не имеют физического ресета). Должно быть `command`.
  2. `homing_speed: 8` по Z через тензодатчик на Toolhead 0. С учетом задержки передачи через мост (10–20 мс) сопло на скорости 8 мм/с успеет продавить стол на 0.12–0.16 мм до остановки мотора Z, что грозит поломкой тензобалки. Допустимая скорость — не более 1.5–2.0 мм/с.
  3. Небезопасные макросы `T0`/`T1` (парковка каретки до смены активного экструдера может приводить к удару голов друг о друга).

## 3. Пошаговый план исправления (Action Plan)

### Этап 1: Исправление ядра прошивки микроконтроллеров (AVR & Generic)
1. **`src/generic/serial_irq.c`**:
   - Перенести активацию `serial_enable_tx_irq()` строго внутрь условия `if (ret > 0)`.
2. **`src/command.c`**:
   - Для `CONFIG_SERIAL_POLLED_SLAVE` заблокировать отправку спонтанного `nak:` при ошибках чужих пакетов.
3. **`src/avr/serial.c` и `src/avr/maestro_router.c`**:
   - Реализовать атомарный захват линии USART0 на время передачи целого кадра:
     - Ввести флаг `tx0_active_frame`.
     - Гарантировать, что локальный Klipper материнки и транзитный поток USART1 передаются строго цельными кадрами без взаимного расщепления.
   - Добавить проверку переполнения FIFO в `maestro_router.c`.
4. **`src/avr/spi.c`, `src/avr/hard_pwm.c`, `src/avr/i2c.c`**:
   - Добавить полную поддержку чипа `CONFIG_MACH_atmega16`.

### Этап 2: Исправление хостового мультиплексора (`host_multiplexer.py`)
1. Перевести открытие `/dev/ttyS0` на `serial.Serial(port, baudrate=250000)`, обеспечивающий гарантированную аппаратную скорость 250 000 бод на Linux через `termios2`.
2. Добавить обработку событий `POLLHUP`/`POLLERR` на PTY с корректным пересозданием виртуального канала без утечки в 100% CPU.

### Этап 3: Тестирование и верификация

2. Проверить чистоту кода, отсутствие регрессий для стандартных конфигураций Klipper.
